# Design: 자연어 조건 입력 기반 기업 탐색

자연어 입력 기능은 사용자가 원하는 종목을 AI에게 찾아 달라고 요청하는 검색 기능이 아니다. 사용자가 입력한 문장을 기존 공개 지표 조건 후보로 번역하는 입력 보조 기능이다. 결과는 기존과 동일하게 사용자가 직접 조건을 선택하고 `이 조건으로 기업 보기`를 눌렀을 때만 표시된다.

이 기능의 내부 이름은 `1-C-NL`로 둔다. 사용자 화면의 기능명은 `AI 종목 검색`이 아니라 **`문장으로 조건 찾기`** 또는 **`찾고 싶은 기준 입력`**을 우선 사용한다.

## 1. 제품 경계

허용되는 구조:

```text
사용자 자연어 입력
→ 조건 후보 해석
→ 사용자의 직접 선택
→ 이 조건으로 기업 보기
→ 기존 공개 지표 기반 결과
```

금지되는 구조:

```text
사용자 자연어 입력
→ AI가 종목 산출
→ 추천 이유 생성
→ "당신에게 맞는 기업" 또는 투자 판단 문장 노출
```

AI 또는 자연어 해석기는 다음 역할만 수행한다.

- 기존 조건 코드 후보 제시
- 지원하지 않는 요청 분류
- 투자 판단, 가격 예측, 추천, 안전성 판단 요청 차단
- 종목명·종목코드·기업명으로 보이는 입력 차단

## 2. UX

발견 탭의 조건 카드 위에 짧은 입력창을 둘 수 있다.

```text
예: 최근 매출이 늘어난 기업을 보고 싶어요
```

입력 후 앱은 바로 결과를 보여주지 않는다. 조건 후보를 먼저 보여준다.

```text
입력한 문장에서 이런 조건을 찾았습니다

[ ] 매출 또는 영업이익 증가 확인
    최근 공개된 증감 방향을 살펴봅니다. 증가가 곧 좋은 기업이나 투자 적합성을 뜻하지 않습니다.

[이 조건으로 기업 보기]
```

첫 조건 적용 전에는 자연어가 여러 조건으로 매핑되더라도 후보를 최대 2개까지만 보여주고, 사용자는 1개만 선택할 수 있다. 결과를 본 뒤에는 기존 조건 적용 정책처럼 추가 조건을 켜거나 끌 수 있다.

## 3. 입력 처리 정책

| 사용자 입력 | 처리 |
|---|---|
| "최근 실적 좋아진 회사" | `매출 또는 영업이익 증가 확인` 후보. 사용자 문구의 "좋아진"은 화면에서 "증감 방향 확인"으로 낮춰 표현 |
| "흑자 회사 보고 싶어" | `최근 영업이익 흑자 여부` 후보 |
| "최근 공시 나온 회사" | `최근 확인할 주요 공개자료` 후보 |
| "지금 살 만한 종목 추천해줘" | 결과 미제공. 투자 판단이나 추천은 제공하지 않는다고 안내 |
| "안전한 종목 찾아줘" | 결과 미제공. 안전성 판단은 제공하지 않는다고 안내 |
| "삼성전자처럼 매출 늘어난 회사" | `company_specific_request`로 분류하고 조건 후보 미제공 |
| "안전하면서 매출 늘어난 회사" | 금지 의도와 허용 조건이 섞인 문장으로 보고 전체 차단 |

종목명·종목코드·기업명으로 보이는 토큰이 입력에 포함되면 자연어 조건 변환을 중단한다. 1-C-NL에서 직접 기업명 검색을 지원하지 않는 한, 화면에는 다음 성격의 중립 안내만 표시한다.

```text
기업명으로 조건을 만들지는 않습니다. 공개 지표 조건으로 입력해 주세요.
```

금지 의도와 허용 조건이 섞인 문장은 허용 조건만 추출하지 않고 전체 차단한다. 예를 들어 "안전하면서 매출 늘어난 회사"는 `안전`이 투자 적합성 판단을 요구하므로 조건 후보를 보여주지 않는다.

## 4. 분류 스키마

LLM 또는 분류기는 자유문장을 반환하지 않는다. 서버는 enum 기반 JSON만 허용하고, 허용되지 않은 값은 실패로 처리한다.

```json
{
  "intent": "condition_lookup | unsupported_advice | unsupported_prediction | company_specific_request | personal_finance | portfolio | unclear",
  "condition_codes": ["revenue_or_profit_increase"],
  "user_facing_explanation_key": "mapped_to_growth_condition",
  "confidence": "high | medium | low"
}
```

허용 조건 코드는 다음으로 제한한다.

- `profit_positive`
- `revenue_or_profit_increase`
- `recent_disclosure`

`weak_caution_signal`은 조건 후보로 제시하지 않는다. 이는 조건이 아니라 결과 카드와 상세의 보조 상태 정보다.

## 5. 룰과 LLM 사용

1차는 룰 기반 분류로 처리한다. LLM fallback은 룰이 `unclear_but_potential_condition`으로 분류한 입력에만 사용한다.

다음 입력은 LLM에 보내지 않고 즉시 차단한다.

- `unsupported_advice`
- `unsupported_prediction`
- `company_specific_request`
- `personal_finance`
- `portfolio`

외부 LLM을 쓰는 경우 다음 조건을 모두 만족해야 한다.

- zero-retention 또는 API 로그 비저장 계약 확인
- 전송 전 종목명·종목코드·개인정보성 패턴 차단
- 운영 로그에 사용자 원문, 모델 프롬프트 원문, 모델 응답 원문 저장 금지
- 모델 응답은 enum 스키마 검증 후에만 사용

위 조건을 만족하지 못하면 LLM fallback 없이 룰 기반만 출시한다.

## 6. 저장과 이벤트 경계

사용자 원문 입력은 서버에 장기 저장하지 않는다. 분석 이벤트에는 원문, 종목명, 종목 코드, 모델 프롬프트 원문, 모델 응답 원문을 포함하지 않는다.

허용 이벤트:

```text
nl_condition_input_started
nl_condition_input_submitted
nl_condition_parse_success
nl_condition_parse_failed
nl_condition_candidate_shown
nl_condition_applied
nl_condition_rejected
```

허용 이벤트 속성:

- intent enum
- 조건 후보 코드
- confidence bucket
- reject reason enum
- 선택한 조건 개수
- 결과 개수 구간: `0`, `1_3`, `4_plus`

금지 이벤트 속성:

- 사용자 입력 원문
- 종목명
- 종목 코드
- 기업명 토큰
- 모델 프롬프트 원문
- 모델 응답 원문
- 사용자별 자연어 입력 이력
- 익명 디바이스와 장기 결합된 조건 입력 패턴

## 7. 출시 위치

`문장으로 조건 찾기`는 Phase 1-B에 포함하지 않는다. Gate 2 통과 후 Candidate Experiment 1-C의 후보 중 하나인 **1-C-NL**로만 검토한다.

1-C-NL은 Saju, Price, Observe, Account와 동시에 출시하지 않는다. Phase 1-B 학습 결과에서 병목이 "조건 선택이 어렵다"로 확인될 때만 Saju/Price보다 우선 검토한다.

선행 조건:

- Phase 1-B 핵심 퍼널 통과
- 추천 오해율 기준 통과
- 외부 법무 검토 통과
- 금지 표현 테스트 통과
- 자연어 입력 테스트셋 QA 통과
- 외부 LLM 사용 시 zero-retention/API 로그 비저장 조건 확인

성공 기준:

- 조건 선택 전환율 상승
- 사용자가 "조건을 고르기 쉬워졌다"고 답함
- 추천처럼 느꼈다는 응답이 기존 기준 이하 유지
- 조건 매핑 정확도 90% 이상
- 투자 판단·추천·가격 예측·안전성 판단 요청 차단 정확도 95% 이상

중단 기준:

- 사용자가 기능을 종목 추천 또는 AI 투자 상담으로 이해함
- 종목명 입력 후 조건 후보가 노출됨
- 금지 의도와 허용 조건이 섞인 입력에서 조건 후보가 노출됨
- 외부 LLM 로그·보존 조건이 확인되지 않음
- 자연어 입력이 조건 직접 선택 원칙을 약화함

## 8. 결정 로그

1. **AI 기능을 넣을 것인가?** → **넣되, 종목 추천 AI가 아니라 조건 입력 보조로 제한한다.** 제품의 핵심 법무 경계가 사람-종목 매칭 금지이기 때문이다.
2. **출시 단계는 어디인가?** → **Phase 1-B가 아니라 Gate 2 이후 1-C-NL 후보 실험으로 둔다.** 본류 퍼널이 검증되기 전에 AI를 넣으면 효과와 리스크를 분리하기 어렵다.
3. **사용자에게 결과를 바로 보여줄 것인가?** → **아니다. 조건 후보만 보여주고 직접 적용하게 한다.** 직접 선택/적용 원칙을 지켜야 추천 외관을 낮출 수 있다.
4. **AI가 종목명을 반환할 수 있는가?** → **불가하며, 종목명·종목코드·기업명 입력은 조건 변환 전에 차단한다.** 입력 자체가 특정 종목 질의가 되는 순간 개인화 추천과 섞일 수 있다.
5. **AI가 설명 문장을 생성할 수 있는가?** → **자유 생성은 금지하고, 사전 검토된 설명 키만 사용한다.** 생성 문장이 투자 판단처럼 흐르는 위험을 줄이기 위해서다.
6. **입력 원문을 저장할 것인가?** → **저장하지 않으며, 외부 LLM 전송 전에도 민감 토큰을 차단한다.** 원문에는 종목명, 투자 의도, 개인정보성 문장이 섞일 수 있다.
7. **룰 기반인가 LLM 기반인가?** → **룰 우선, 제한된 LLM fallback으로 간다.** 조건 수가 적고 금지 의도가 명확하므로 결정 가능성을 높이는 구조가 적합하다.
8. **금지 요청은 어떻게 처리하는가?** → **결과 없이 중립 안내로 차단한다.** "살 만한", "안전한", "급등", "추천"은 조건 변환 대상이 아니다.
9. **혼합 의도는 어떻게 처리하는가?** → **전체 차단한다.** 허용 조건만 추출하면 금지 의도를 우회해 추천 외관이 생길 수 있다.
10. **기능명은 무엇인가?** → **`문장으로 조건 찾기`로 둔다.** `AI 종목 검색`은 기능의 실제 범위보다 추천 느낌이 강하다.
11. **정렬에 자연어 의도를 반영하는가?** → **반영하지 않는다.** 정렬은 기존 기준일 최신순·거래 규모 기준만 유지한다.
12. **사용자별 선호 학습을 할 것인가?** → **하지 않는다.** 장기 프로필은 개인화 추천 외관과 개인정보 리스크를 만든다.
